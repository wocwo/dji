# 为什么这样设计：一个 DJI 手册 Agent 的取舍

## 问题不是“把 PDF 接给大模型”

DJI 手册有三个特点，决定了普通 RAG Demo 不够用：

1. **页面即证据**：用户问“Mini 4 Pro 电池低温怎么保养”，答案必须能回到具体手册页；只给一段相似文本，无法验证。
2. **参数密集**：温度、限高、返航距离、充电时间经常在表格里，差一个单位就是错误答案。
3. **故障描述不完整**：用户说“炸机了”，手册不会给“看照片判断损伤”的章节，必须承认手册没有覆盖，再给通用排查。

所以系统目标不是“生成得像”，而是：

> **每个关键事实有出处；手册没有的，明确说没有；图片只做观察，不冒充手册。**

## 总体架构

```mermaid
flowchart LR
  U[Web / CLI / HTTP] --> A[认证与用户隔离]
  A --> S[会话记忆 SQLite]
  A --> R[Agent Runtime]
  R --> T[工具: 手册检索 / 取页 / 计算 / 笔记]
  T --> K[页面级 JSONL BM25 + 规则重排 + ONNX reranker]
  R --> G[Evidence Gate / Grounding / Claim Verifier]
  G --> O[带 [S1] 的回答]
  O --> C[引用与 Trace]
  A --> V[图片: OCR + Qwen3-VL]
  V --> R
```

关键点：**检索不是应用，而是 Agent 的一个工具**。Agent 可以先搜、再取页、再补搜；不是一次 top-k 就结束。

## 为什么用页面级 BM25，而不是只做向量库

向量库擅长语义相似，但手册问答里有两类查询它不占优：

- 精确参数：`-10°C`、`30 m`、`0.5-30 m`；
- 页码/版本：用户需要知道依据哪一页。

因此当前默认是：

```text
JSONL 页面/表格记录
  → BM25 词法召回
  → 规则重排（机型、章节、页码、参数匹配）
  → 本地 ONNX bge-reranker
  → 页面级 citation
```

这比“只维护一个 Chroma 集合”更土，但更可解释、启动更轻、离线可复现。向量库仍然保留为可选后端，用于语义召回；不是被否定，而是不作为唯一真相。

## 证据门控：先允许“不知道”

系统里有几层防线：

- **Evidence Gate**：没有检索证据时，不允许模型直接给手册结论；
- **Grounding**：回答中的 `[S1]` 必须对应真实 citation；
- **Claim Verifier**：高风险答案检查关键 claim 是否有证据；
- **Fact Coverage**：检查问题里的关键事实是否被回答覆盖；
- **故障排查 fallback**：手册无覆盖时，输出“通用建议（非手册）”，并追问机型/现象。

这些机制会降低“答得快”，但换来了可审计。对维修/安全场景，这个取舍是值得的。

## 长上下文：摘要 + 历史检索，而不是无限塞

多轮对话不是把全部历史拼进 prompt。当前顺序是：

```text
system
+ 滚动摘要（session_summaries）
+ 同 session 的历史相关轮次（词面相关度）
+ 最近 6 轮
+ 当前问题
```

- 摘要按窗口增量更新；
- 旧轮次只在相关时召回；
- 最近轮次保证指代和语气连续。

这样 fast 模式约 4k token，normal 约 9k token，而不是随轮数线性膨胀。

## 三种模式不是“快/慢”这么简单

| 模式 | 检索 | LLM | 校验 | 典型延迟 |
|------|------|-----|------|----------|
| fast | 预检索 1 次，top_k=3 | 1 次 | 关闭 claim/coverage | 5–8s |
| normal | 多步检索，top_k=6 | 2 次 | 保留高风险校验 | 8–15s |
| auto | 按高风险词路由 | 动态 | 动态 | 5–15s |

`auto` 不是“随便选一个”，而是把电池、充电、固件、返航、坠机、进水等词视为高风险，走 normal；其他走 fast。

## 图片：观察与事实必须分开

图片链路是：

```text
上传 → 压缩/去 EXIF → RapidOCR（文字）
                    → Qwen3-VL（结构化观察）
                    → 图片观察（非手册）
                    → 与手册证据合并回答
```

视觉模型只输出：

- 机型猜测
- 屏幕文字
- 指示灯
- 可见损伤
- 置信度 / 不确定项

它**不做维修诊断**，也不能生成 `[S1]` 页码。回答中必须区分：

```text
[S1] 手册明确
[V1] 图片观察（非手册）
[推断] 基于图片 + 手册
```

### 为什么最终用 data URI

最初把图片写临时文件交给 DashScope SDK，SDK 会先上传 OSS，服务端一次结构化观察要 43–50 秒。改成 base64 data URI 后，同一模型直连约 2–3 秒，公网约 5–20 秒。  
这不是模型替换，而是**传输路径**问题。

### 为什么没有继续换模型

当前网关实测：

- `qwen3-vl-plus`：可用；
- `qwen-vl` / `qwen-vl-plus` / `qwen-vl-max`：404；
- `qwen-vl-ocr`：可用，但按要求不启用。

所以不是“换名字”能解决，必须换网关或账号。

## 评测：把“感觉不错”变成数字

评测分两层：

1. **文本端到端**：24 条 holdout，检查状态、引用命中、关键 claim、数字；
2. **视觉**：错误截图、产品图、空白图，检查文字、机型、是否幻觉损伤。

视觉评测故意包含**负样本**：正常产品图必须 `visible_damage={}`，空白图不能编造损伤。  
这比只测“能不能识别”更重要，因为维修场景最危险的是**自信地胡说**。

## 安全与多用户

公开 Demo 不能所有人共用一份会话。当前实现：

- Basic 用户名映射 `AGENT_USERS`；
- session 命名空间 `u:<user>:<id>`；
- job 记录 owner，越权读取返回 404；
- token 不再放 URL query；
- UI token 改为 HttpOnly cookie；
- 限流按用户。

这仍是单进程轻量隔离，不是生产多租户；但足以避免“A 看到 B 的对话”这种明显问题。

## 已知失败与不做的事

- 没有真实坠机损伤图集，不能宣称视觉损伤识别已达标；
- `qwen3-vl-plus` 公网仍有 5–20s 延迟，未做异步视觉；
- 图片历史不落盘，刷新后聊天里不保留；
- 手册数据有版权，开源只能放演示语料；
- 没有 OIDC、配额、审计日志，生产需补；
- 没有 token 级流式输出，目前是任务进度轮询。

## 一句话

这个项目的核心不是“接了一个大模型”，而是：

> **把手册问答拆成可验证的证据链：检索、取页、引用、门控、图片观察、用户隔离，每一层都能单独解释和测试。**
